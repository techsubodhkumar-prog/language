Activity Discovery Platform
A practical implementation roadmap for a mobile-first platform where people discover activities, create plans, request to join,
receive host approval, and coordinate in activity-specific groups.
Document version 1.0
Document status Development baseline
Client Flutter / Dart mobile application
Backend and data HTTPS API, PostgreSQL, real-time messaging, push notifications
Related artifacts SRS, architecture/database diagrams, UML/workflow diagrams, UI/UX design
Core delivery principle: build one complete, testable end-to-end user journey first. Do not build every screen
independently before connecting the workflow.
Prepared as an implementation guide. Technology choices can be refined during technical spikes, but business rules and security constraints in this
plan should remain enforced.

ACTIVITY DISCOVERY PLATFORM
1. Development objectives and scope
The first release should prove that a person can sign up, select interests, discover an activity, request to join, receive a host
decision, and coordinate with approved members. Supporting features are delivered after this core flow works reliably.
MVP scope
l Identity: registration, sign-in, sign-out, password reset, session/token handling.
l Onboarding: profile basics and selected interests/categories.
l Activities: create, edit, publish, browse, search, filter, view details, cancel and complete.
l Membership: request to join, withdraw request, host approve/reject, leave activity, capacity enforcement.
l Coordination: activity group chat available only to the host and approved members.
l Notifications: join request, decision, activity update/cancellation, reminder.
l Safety: block/report entry points, privacy-aware location display, basic moderation queue.
Not required for the first MVP unless explicitly added to the SRS
l Payments, subscriptions, public social feed, live video, advanced recommendation ML, complex event ticketing, or full
identity verification.
l Do not collect more personal data than necessary to deliver discovery and coordination.
Definition of MVP success
Measure Release target
Core journey Registration fi interests fi discovery fi request fi host decision fi group chat works
end-to-end.
Capacity correctness No activity can exceed its configured confirmed-member capacity under concurrent approvals.
Authorization Users cannot edit another host’s activity or read chats they are not authorized to access.
Reliability Critical journey tests pass in CI and on a real Android device before release.
Safety Block/report flows are reachable and produce auditable server-side records.

Backend language/framework decision
Choose one backend framework before implementation and document the decision. The critical requirement is not the
language; it is consistent server-side validation, database transactions, authorization, observability, and testability. Keep the
API contract independent of Flutter widgets.
Environment separation
l Local: developer machine and disposable/test database.
l Staging: production-like configuration, synthetic accounts/data, end-to-end testing.
l Production: restricted secrets, backups, monitoring, and controlled database migrations.
Architecture rule
Flutter must never connect directly to PostgreSQL or contain database credentials. All trusted business
decisions are made by the backend. The client may improve usability with early validation, but server
validation is authoritative.

4. Milestone-based delivery plan
Use milestone exits rather than calendar promises. Each phase is complete only when its deliverables and acceptance
checks pass.
Milestone Work Exit criteria
M0 — Foundation Repo, Flutter app shell, backend skeleton, database Clean build, lint/static analysis, health endpoint,
migration framework, CI documented local setup.
M1 — Identity & Auth, profile, interests, session handling New user can register, sign in, select/edit
onboarding interests, and sign out.
M2 — Activity Create/publish activity, list/detail, search and filters Host can publish; other users can discover and
discovery view details.
M3 — Join workflow Request, withdraw, approve/reject, leave, capacity Every state transition is authorized; concurrent
transactions approvals cannot overfill.
M4 — Chat & Activity chat access control, in-app notifications, push Only approved members/host can access chat;
notifications integration key state changes notify correctly.
M5 — Safety & polish Report/block, accessibility, empty/error states, privacy Safety actions persist; blocked-user rules apply
review server-side.
M6 — Release Regression, security, performance, device tests, No open critical/high defects; rollback and
candidate backups, release notes support procedures tested.
Recommended working rhythm
l Plan one small feature slice; define acceptance criteria before coding.
l Create a branch and small reviewable commits; avoid mixing unrelated features.
l Run formatter, static analysis, unit tests, and relevant integration tests before merging.
l Demonstrate the working feature on a device or staging environment at each milestone.
l Keep a bug log with severity, reproduction steps, owner, fix version, and retest result.

5. Backend rules that must be implemented early
These are correctness and security rules, not optional UI behavior.
Rule Required implementation
Activity ownership Only the authenticated host (or authorized moderator) may edit, publish, or cancel the activity.
Membership uniqueness Add a unique database constraint for (activity_id, user_id) so duplicate requests/memberships cannot
be created.
Atomic capacity Approval must recheck confirmed count and update membership in a transaction/locking strategy.
Two approvals racing for the last spot must not both succeed.
Membership states Model requested, approved, rejected, withdrawn/left, and removed explicitly. Define which transitions
are allowed.
Chat authorization Authorize every room join, history fetch, and send operation on the server; never trust client-supplied
activity IDs alone.
Blocking Apply block rules to discovery, joining, messaging, and future contact where applicable; check on the
server.
Location privacy Show approximate location before approval when appropriate; avoid exposing home/private locations
or precise coordinates unnecessarily.
Rate limiting Limit sign-in attempts, join requests, message sending, report submission, and other abuse-prone
endpoints.
Audit trail Record important moderation and membership decisions with actor, timestamp, target, and outcome.
Notifications Treat notification delivery as retryable; do not let push failure roll back a successful membership
transaction.
Example API surface
Area Example endpoints (illustrative; finalize in API specification)
Auth POST /auth/register, POST /auth/login, POST /auth/logout, POST /auth/refresh
Profile GET/PATCH /me, GET/PUT /me/interests
Activities POST /activities, GET /activities, GET /activities/{id}, PATCH /activities/{id}, POST /activities/{id}/cancel
Memberships POST /activities/{id}/join, GET /activities/{id}/requests, POST /memberships/{id}/approve, POST
/memberships/{id}/reject, POST /activities/{id}/leave
Chat GET /activities/{id}/messages, POST /activities/{id}/messages; real-time channel auth
Safety POST /reports, POST /blocks, DELETE /blocks/{userId}

Risk-based priority
l P0 / critical: unauthorized access, over-capacity membership, data loss, cross-user chat leakage.
l P1 / high: login blocked, host cannot approve, activity cannot be created, key notifications absent.
l P2 / medium: filters wrong, layout defects, non-critical notification delay.
l P3 / low: minor visual inconsistency or copy issue with a safe workaround.

7. Core test cases and acceptance checks
ID Scenario Expected result
TC-01 Register with valid data Account is created; duplicate email/identity is handled safely; no
plaintext password is stored.
TC-02 Submit invalid sign-in details repeatedly Generic error response; rate limit/lockout policy applied without leaking
account existence unnecessarily.
TC-03 Create activity with end time before start time Validation blocks submission and identifies the field to correct.
TC-04 Unauthenticated user attempts to create Backend returns unauthorized; no activity record is created.
activity
TC-05 Non-host edits or cancels another user’s Backend denies the request; original activity remains unchanged.
activity
TC-06 User requests to join a published activity with One pending request is created; duplicate taps do not create
capacity duplicates.
TC-07 Host approves request when a spot remains Membership becomes approved; count updates; notification is queued;
chat access is granted.
TC-08 Two host approvals race for the final spot At most one approval succeeds; the other receives a clear full/capacity
response.
TC-09 User tries to read chat without membership Backend denies access to history and real-time room; no messages
leak.
TC-10 Approved user leaves activity Membership changes to left; chat access is removed according to
policy; capacity is recalculated.
TC-11 Host cancels an activity Status changes; participants are notified; joining and chat posting follow
cancellation policy.
TC-12 A user blocks another user Block is persisted and enforced by server-side discovery/join/chat rules
as defined.
TC-13 Push provider is temporarily unavailable Core action still succeeds; notification retries or remains in-app; no
duplicate membership change.
TC-14 Network drops during form submission UI shows retryable state; user input is retained; repeated submission is
idempotent where applicable.
TC-15 User reports a person/activity Report is stored with status and audit data; user receives confirmation
without revealing internal moderation data.
Release gate
All P0/P1 tests pass; no open critical/high security defect; migrations work on a clean database;
restore/rollback instructions are available; and the core journey passes on at least one physical Android device
plus staging.

8. CI/CD, environments, and release management
Suggested pull-request pipeline
Stage Checks
1. Quality Format, lint/static analysis, unit tests, dependency vulnerability scan.
2. Backend Unit/API integration tests against an isolated database; migration checks.
3. Mobile Flutter tests, Android debug build, widget tests.
4. Contract Validate API schema/examples and error response consistency.
5. Merge Require green checks and review; protect main branch.
6. Staging Deploy backend, apply reviewed migrations, install build, run smoke/E2E tests.
7. Release Tag version, generate signed Android artifact, publish release notes, monitor rollout.
Release checklist
l Use separate production secrets; never commit API keys, signing keys, database passwords, or private service
credentials.
l Confirm Android app signing and version/build numbers; verify permissions and privacy disclosures.
l Back up the production database before risky migrations and test restore procedures in advance.
l Use backward-compatible migrations when possible; have a rollback/forward-fix plan.
l Monitor crashes, API error rates, login failures, join/approval failures, notification delivery, and unusual abuse reports.
l Release gradually if the distribution channel supports it; pause rollout if critical metrics regress.
Operational monitoring
Logs should contain correlation/request IDs and useful event context, but avoid passwords, authentication tokens, private
messages, precise location, or unnecessary personal information. Define retention and access permissions for logs and
reports.

9. First implementation sprint checklist
Use this as the initial working checklist. Complete the items in order and demonstrate each result before moving on.
n Create the repository and document how to run mobile and backend locally.
n Set up Flutter formatting, static analysis, test folder, routing, and shared theme.
n Choose the backend framework; add health endpoint, configuration validation, and API error format.
n Create PostgreSQL migrations for users, interests, user_interests, activities, memberships, and blocks.
n Implement authentication and a protected /me endpoint.
n Build onboarding to save interests and profile basics.
n Implement activity create/list/detail endpoints and Flutter screens.
n Implement join request and host decision with transactional capacity enforcement.
n Add tests for authorization, duplicate requests, and concurrent approvals before adding chat.
n Implement chat room authorization and message persistence.
n Add in-app notifications, then push notifications.
n Add report/block, test privacy rules, and prepare staging smoke tests.
Go / no-go decision
Go: critical user journeys work, P0/P1 tests pass, capacity and authorization tests pass, no critical/high defect is open,
monitoring is active, and rollback/restore steps are known.
No-go: chat or activity data can leak across users, capacity can be exceeded, host-only actions lack server checks,
production secrets are exposed, or core flows are unreliable.
Document end — keep this plan synchronized with the SRS, API specification, architecture, database schema, and UI/UX designs whenever
requirements change.
